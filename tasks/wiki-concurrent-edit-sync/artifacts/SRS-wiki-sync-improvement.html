미확정 사항

미확정 사항 요약 — 이 문서는 다음 3건을 의도적으로 열어 두었다. §11 참조. ① FR-05 (a)블록 내부 병합 / (b)우선순위+고지 택일 ② FR-04 블록 식별자의 저장 본문 포함 여부 ③ OtService 재활용 여부. 또한 §10 선행 조사 5건이 미수행 상태이며, 특히 §10-5(다중 인스턴스 여부)는 단계 3 착수 전 필수다.

1. 개요

1.1 목적

ARMS wiki 동시 편집에서 보고된 두 증상 — (가) 원격 반영 시 블록 중복 삽입, (나) 동시 편집 내용의 유실·오반영 — 을 해소하기 위해, 동기화 계층이 무엇을 만족해야 하는가를 정의한다. 구현 방법이 아니라 만족해야 할 성질과 그 검증 방법을 기술한다.

1.2 범위

구분 대상
In scope 위키 편집기의 문서 변경 전파 프로토콜, 클라이언트 diff 기준선 관리, 서버 수용·브로드캐스트 정책, 저장 시 동시성 제어, 원격 커서 표현, 관측성
Out of scope CKEditor4 → 타 에디터 교체, STOMP/SockJS → 타 전송 교체, 위키 본문 스키마 변경, 권한·인증 체계

1.3 전제

  • 기존 스택 유지: CKEditor4 + STOMP/SockJS + Spring(Broker-Hub) + Redis.
  • 이 SRS의 사실 근거는 정적 코드 분석이다. 분석서가 가설로 표기한 항목(B-3·B-4·B-5, Caveat 7)은 요구사항의 전제로 삼지 않고 §10 선행 조사 항목으로 분리한다. 해당 조사 결과에 따라 관련 FR의 우선순위·존폐가 결정된다.

1.4 용어

용어 정의
블록 CKEditor body의 직계 자식 엘리먼트 1개 (getEditorBlocks가 뽑는 단위)
기준선(base) 클라이언트가 다음 diff를 계산할 때 "직전 상태"로 쓰는 블록 배열 (현 lastBlocks)
ops retain/insert/delete/replace 시퀀스
rev 서버가 문서에 부여하는 단조 증가 개정 번호
수렴(convergence) 같은 op 집합을 받은 모든 클라이언트의 문서가 동일해지는 성질

2. 현행 시스템과 문제

2.1 현행 데이터 흐름

[송신] keyup → 150ms debounce → getEditorBlocks() → computeBlockDiff(lastBlocks, current)
       → lastBlocks 선(先)전진 → publish "/app/selection"
[서버] EditorController#handleSelectionUpdate
       → Redis에 사용자 selection 상태로 저장 → convertAndSend(원본 그대로, 발신자 포함 전 구독자)
[수신] "/topic/sessions/{sid}/selections/document/{did}"
       → session-manager.js에서 발신자 필터 → onContentsChange → applyBlockDiff(DOM 직접 조작)

2.2 구조적 문제 요약

  1. 단일 채널·무검증 릴레이. 서버는 ops를 해석·검증·정렬하지 않는다. 순번도 rev도 없다. 서버에 OtService(revision·history)가 존재하나 위키 편집기 클라이언트는 그 경로를 쓰지 않는다.
  2. 기준선이 원격 반영을 반영하지 않는다. applyBlockDiff는 DOM만 바꾸고 lastBlocks를 갱신하지 않으며, dataReady도 발생시키지 않아 기존 재동기화 방어가 걸리지 않는다.
  3. 적용 가드가 비대칭이다. delete/replace는 대상이 없으면 조용히 건너뛰고, insert는 대상 유무와 무관하게 항상 성공한다 → 불일치가 "중복 단조 증가"로 나타난다.
  4. 최소 편집 단위가 블록 통째(outerHTML)다. 같은 문단을 두 사람이 만지면 병합 없이 통째 교체된다.
  5. 전달 실패가 침묵한다. 기준선을 publish 전에 전진시키고, 연결 실패 시 대기 큐를 비우며, ack·재시도·시퀀스가 없다.
  6. 저장이 last-writer-wins. 버전·ETag 없이 본문을 덮는다.

2.3 추가 관측 [코드 확인, 분석서 미기재]

EditorController.java:179는 diff JSON이 실린 selection.message를 사용자의 "selection 상태"로 Redis에 영속화한다. 즉 콘텐츠 변경이 커서 상태 저장소를 오염시킨다. 채널 분리(FR-16)의 부수 근거이며, 이번 두 증상의 직접 원인은 아니다.

3. 설계 목표·원칙

G. 목표

ID 목표
G-1 수렴 보장. 동일한 편집 이벤트 집합을 받은 모든 참여자의 문서 블록열이 최종적으로 동일하다
G-2 무손실. 사용자가 확정한 입력은 전달 실패·재연결·충돌 어느 경우에도 소멸하지 않거나, 소멸 시 사용자에게 고지된다
G-3 설명 가능한 semantics. 충돌 시 결과가 "알 수 없음"이 아니라 문서화된 규칙으로 결정된다
G-4 자가 복구. 불일치가 발생하면 감지되고, 사용자 개입 없이 일관 상태로 복원된다
G-5 점진 적용. 각 단계가 독립 배포 가능하며, 미적용 클라이언트와 공존해도 현행보다 나빠지지 않는다

P. 원칙

  • P-1 침묵 금지. 적용 불가·전송 실패·정화 드롭은 조용히 통과시키지 않는다. 최소한 관측 가능해야 한다.
  • P-2 단일 진실원. 문서의 권위 상태는 한 곳(서버 rev)에만 둔다. 클라이언트는 그에 대한 캐시다.
  • P-3 기준선 불변식. "내가 다음 diff를 계산하는 기준"과 "상대가 그 diff를 적용할 대상"은 항상 같아야 한다. 이 불변식이 깨지는 코드 경로를 남기지 않는다.
  • P-4 대칭 가드. 적용 op는 종류에 관계없이 동일한 선행조건 검사를 받는다. 어떤 op만 "무조건 성공"하지 않는다.
  • P-5 기존 방어 존치. IME 조합 차단, 150ms debounce, 커서 요소 제외는 회귀 금지 대상이다.

4. 기능 요구사항

우선순위: P0=즉시(증상 직접 원인), P1=구조 개선, P2=정리·안전망. 각 FR은 "만족해야 할 성질"이며 구현 수단을 규정하지 않는다.

FR-01 — 원격 반영 후 기준선 일치

설명 원격 ops를 문서에 반영한 직후, 클라이언트의 diff 기준선은 반영 후 실제 문서 상태와 동일해야 한다. 문서 상태를 바꾸는 모든 경로(원격 반영, setData, 문서 전환, 스냅샷 복원)에 대해 이 불변식이 성립해야 한다.

근거 원인 A-1 (주원인)

수용 기준 - AC-01-1: A·B 접속 상태에서 B가 문단을 추가 → A가 수신 → A의 기준선 == A의 현재 블록열이다. (자동화 테스트: 반영 직후 기준선과 getEditorBlocks() 결과의 배열 동등 비교) - AC-01-2: 분석서 A-1 재현 시나리오(7단계)를 그대로 수행했을 때 B의 문서에 중복 블록이 생기지 않는다. - AC-01-3: 원격 반영 직후 로컬에서 아무 입력도 하지 않은 상태에서 강제로 diff를 계산하면 retain만 나온다(변경 op 0개).

우선순위 P0

FR-02 — op 적용 가드의 대칭성과 실패 표면화

설명 ops 적용 시 모든 op 종류는 동일한 선행조건(대상 인덱스 존재 여부, 정화 후 노드 존재 여부)을 검사해야 한다. 어떤 op도 선행조건을 만족하지 않은 채 문서를 변경해서는 안 된다. 선행조건 위반이 1건이라도 발생하면 해당 배치 전체를 적용하지 않고, 불일치 사실을 관측 가능한 형태로 남기고 재동기화 절차(FR-14)를 개시해야 한다.

근거 원인 A-2 (중복 단조 증가의 직접 원인), B-4 부분

수용 기준 - AC-02-1: 수신자 블록 수보다 큰 인덱스를 참조하는 ops를 인위적으로 주입하면 문서가 변경되지 않고 불일치 이벤트가 1건 기록된다. - AC-02-2: insert가 대상 위치 없이 문서 끝에 무조건 추가되는 동작이 더 이상 발생하지 않는다(같은 주입 테스트에서 블록 수 불변). - AC-02-3: 부분 적용(ops 일부만 반영된 중간 상태)이 관측되지 않는다.

우선순위 P0

FR-03 — 자기 발신 메시지 필터의 단일화

설명 발신자 자신에게 되돌아온 메시지(에코)의 무시 책임은 한 계층에만 두고, 그 계층에서 메시지 종류와 무관하게 일관되게 적용되어야 한다. 상위 계층의 중복 방어는 제거하거나, 유지한다면 "도달 불가능한 이중 방어"임을 명시해야 한다.

근거 원인 A-3 (분석서에서 반증됨 — 현 증상의 원인 아님. 회귀 방지·코드 명확화 목적)

수용 기준 - AC-03-1: 에코 필터 지점이 코드 전체에서 1곳이며, diff/cursor 및 향후 추가 타입에 공통 적용된다. - AC-03-2: 자신이 보낸 메시지가 문서에 반영되지 않음을 회귀 테스트가 검증한다(서버 에코 정책이 발신자 포함 브로드캐스트로 유지되는 한).

우선순위 P2

FR-04 — 블록의 안정 식별

설명 블록의 동일성 판정은 내용 문자열 비교나 위치 인덱스에 의존해서는 안 되며, 블록 생애주기 동안 불변인 식별자로 판정되어야 한다. 동일 내용 블록이 여러 개 있어도 어느 블록을 가리키는지 모호하지 않아야 하고, 앞선 블록의 삽입·삭제로 인해 참조가 어긋나지 않아야 한다.

근거 원인 A-4, A-2 (구조적 제거), B-3 부분(순서 역전 내성)

수용 기준 - AC-04-1: 빈 문단(<p><br></p>)이 5개 연속인 문서에서, 그중 3번째만 수정했을 때 모든 참여자에게 3번째만 반영된다. - AC-04-2: 동일 문구 블록이 반복되는 문서에서 중간 블록을 삭제해도 다른 참여자에게서 엉뚱한 블록이 삭제되지 않는다. - AC-04-3: 두 개의 ops 배치를 의도적으로 역순 적용해도 최종 문서가 정순 적용과 동일하거나, 불일치가 감지되어 FR-14 경로로 복구된다. - AC-04-4: 식별자는 저장 본문에 포함되더라도 렌더링·검색·기존 위키 표시에 영향을 주지 않는다(또는 저장 시 제거된다). 어느 쪽인지 설계 시 확정해야 한다.

우선순위 P1

FR-05 — 동일 블록 동시 편집의 결정된 semantics

설명 두 참여자가 같은 블록을 동시에 편집한 경우의 결과는 문서화된 규칙으로 결정되어야 하며, 다음 중 하나를 만족해야 한다. - (a) 블록 내부 변경이 병합되어 양쪽 입력이 모두 보존된다, 또는 - (b) 규칙(예: 서버 수용 순서)에 따라 한쪽이 우선하고, 패배한 쪽의 사용자에게 자신의 입력이 반영되지 않았음이 고지된다.

어느 경우에도 "내가 쓴 것이 상대 화면에, 상대 것이 내 화면에" 남는 비대칭 상태가 지속되어서는 안 된다.

근거 원인 B-1 (시나리오 ① 소실, ② 핑퐁)

수용 기준 - AC-05-1: 두 브라우저가 같은 문단을 동시에 편집한 뒤 양쪽 입력을 멈추고 3초 경과 시, 두 화면의 해당 블록 내용이 동일하다. - AC-05-2: (b) 채택 시, 패배한 참여자에게 고지가 표시되며 그의 입력이 클립보드·복구 버퍼 등으로 회수 가능하다. - AC-05-3: 원격 반영으로 인해 로컬 캐럿이 문서 밖으로 튀거나 다른 블록으로 이동하지 않는다(캐럿 블록·오프셋 보존율 측정). - AC-05-4: 분석서 B-1 시나리오 ②를 10회 반복해도 3회차 이후 화면 뒤집힘이 재발하지 않는다.

우선순위 P1

FR-06 — 전송 확정 전 기준선 전진 금지

설명 클라이언트의 diff 기준선은 해당 변경분이 서버에 확실히 전달된 이후에만 전진해야 한다. 전달 실패·미연결·거부 시 기준선은 이전 값을 유지하여, 다음 diff 계산에 그 변경분이 다시 포함되어야 한다.

근거 원인 B-2

수용 기준 - AC-06-1: 전송 경로를 강제 실패시킨 상태에서 3회 입력 후 전송을 복구하면, 3회분 변경이 모두 상대에게 반영된다. - AC-06-2: 세션 미확립 상태(sessionId/documentId 미설정)에서 발생한 입력이 이후 세션 확립 시 유실 없이 전파되거나, 전파 불가임을 사용자에게 고지한다. - AC-06-3: 어떤 경로로도 "기준선은 전진했으나 상대는 못 받은" 상태가 만들어지지 않는다(계약 테스트로 검증).

우선순위 P0

FR-07 — 연결 단절·재연결 시 무손실

설명 연결 실패 및 자동 재연결 과정에서 미전송 변경분을 폐기해서는 안 된다. 재연결 후에는 (i) 미전송 변경분이 전송되거나, (ii) 서버 최신 스냅샷으로 재정박한 뒤 사용자의 로컬 변경분이 재계산되어 전송되어야 한다. 구독 복구가 부분 실패한 경우 그 사실이 감지되어야 하며, 송신은 되는데 수신은 끊긴 상태로 편집이 계속되어서는 안 된다.

근거 원인 B-2, Caveat 7(가설 — §10-4 조사 결과에 따라 (iii) 항목 확정)

수용 기준 - AC-07-1: 네트워크를 5초 차단하고 그 사이 계속 타이핑한 뒤 복구했을 때, 차단 구간 입력이 상대 화면에 반영된다(또는 명시적 고지 후 사용자가 복구할 수 있다). - AC-07-2: 구독 복구 중 예외가 발생하면 편집이 읽기 전용으로 전환되거나 재접속이 재시도되며, 아무 표시 없이 편집이 계속되지 않는다. - AC-07-3: 재연결 후 수신 구독이 중복되지 않는다(동일 메시지 2회 반영 없음).

우선순위 P0

FR-08 — 전파 순서의 결정성

설명 동일 문서에 대한 변경 메시지는 모든 수신자에게 동일한 순서로 적용되어야 한다. 전송 계층이 순서를 보장하지 않더라도, 애플리케이션 계층이 순서를 판정하고 어긋난 메시지를 감지·처리할 수 있어야 한다.

근거 원인 B-3 (설정 부재는 사실, 실제 역전 발생은 미검증 가설 — §10-1 조사 선행)

수용 기준 - AC-08-1: 모든 변경 메시지가 문서 단위 단조 증가 순번을 가진다. - AC-08-2: 순번이 건너뛰거나 역전된 메시지를 수신하면 즉시 적용하지 않고 FR-14 재동기화로 처리한다. - AC-08-3: 부하 테스트(참여자 3인 × 초당 5회 입력 × 60초)에서 최종 문서가 3인 모두 동일하다. - AC-08-4: 브로커 발행 순서 보존 설정 여부가 명시적으로 결정·기록되어 있다(기본값 의존 금지).

우선순위 P1 (§10-1 결과가 "역전 실재"면 P0로 승급)

FR-09 — 정화 정책과 편집 허용 정책의 정합

설명 원격 HTML 정화가 제거하는 요소 집합과 에디터가 생성·허용하는 요소 집합이 불일치해서는 안 된다. 불일치가 불가피한 경우(보안상 반드시 제거해야 하는 요소), 그 블록은 "송신자에는 있고 수신자에는 없는" 상태로 남아서는 안 되며, 정화로 인해 내용이 소실되었다는 사실이 양측에서 관측 가능해야 한다.

근거 원인 B-4 (비대칭은 사실, 실제 드롭 발생은 미검증 가설 — §10-2 조사 선행)

수용 기준 - AC-09-1: 에디터가 생성 가능한 모든 블록 유형 목록에 대해, 정화를 통과한 결과가 원본과 의미적으로 동등함을 케이스별로 검증한 표가 존재한다. - AC-09-2: 정화로 노드가 소실되면 드롭 이벤트가 기록되고, 해당 배치는 FR-02에 따라 적용되지 않는다. - AC-09-3: 보안 요구(스크립트·이벤트 핸들러·javascript: URL 차단)는 완화되지 않는다.

우선순위 P1

FR-10 — 원격 커서 표현의 문서 비침입

설명 원격 참여자의 커서·이름표는 문서 콘텐츠 모델에 영향을 주어서는 안 된다. 구체적으로 (i) 블록 추출·diff 계산에 포함되지 않고, (ii) 저장 본문에 포함되지 않으며, (iii) 원격 반영으로 파괴되지 않아야 한다.

근거 원인 B-5 (경로는 사실, 저장본 혼입은 미검증 가설 — §10-3 조사 선행)

수용 기준 - AC-10-1: 참여자 2인 이상 상태에서 저장한 본문에 커서 관련 마크업이 0개다(저장된 HTML 문자열 검사). - AC-10-2: 저장 후 재조회한 문서에 타 사용자 이름 라벨이 나타나지 않는다. - AC-10-3: 원격 ops 반영 후에도 표시 중이던 원격 커서가 유지되거나 즉시 재계산된다.

우선순위 P1 (§10-3에서 혼입 확인 시 P0)

FR-11 — 저장 시 낙관적 동시성 제어와 저장 사실의 전파

설명 문서 저장은 저장 시작 시점에 클라이언트가 알고 있던 문서 버전을 근거로 수행되어야 하며, 그 사이 다른 저장이 있었다면 무조건 덮어쓰지 않고 충돌로 처리되어야 한다. 또한 저장이 성공하면 같은 방의 다른 참여자 전원에게 그 사실과 새 버전이 통지되어야 한다.

근거 원인 B-6

수용 기준 - AC-11-1: A가 저장한 뒤 B(구 버전 기준)가 저장을 시도하면 요청이 거부되고 B에게 충돌이 고지된다. - AC-11-2: 충돌 시 B는 최신 본문을 받아 재정박할 수 있으며, B의 미반영 변경이 자동 폐기되지 않는다. - AC-11-3: A가 저장하고 방을 나간 뒤에도 B의 화면에 "저장됨 / 새 버전 있음" 상태가 표시된다. - AC-11-4: 단독 편집(참여자 1인) 저장 흐름은 기존과 동일하게 동작한다(회귀 없음).

우선순위 P1

FR-12 — 세션 진입 시 서버 문서 상태의 정합

설명 편집 세션 진입 시 서버에 등록되는 문서 초기 내용은 실제 문서 본문이어야 하며, 비어 있거나 null이어서는 안 된다. 서버가 브로드캐스트하는 문서 상태(content·revision)는 항상 유효한 값이어야 한다.

근거 원인 B-7 (서버 권위 도입의 선행 차단 요인)

수용 기준 - AC-12-1: 문서 진입 직후 서버가 보유한 문서 내용이 클라이언트 본문과 동등하다. - AC-12-2: 서버가 브로드캐스트하는 문서 상태의 content가 null이 아니다. - AC-12-3: 문서 전환(다른 위키 문서로 이동) 시에도 AC-12-1이 성립한다.

우선순위 P0 (FR-13의 전제 조건)

FR-13 — 서버 권위 수용·거부

설명 서버는 변경 메시지를 무조건 중계해서는 안 된다. 각 변경은 자신이 기준한 문서 개정(rev)을 함께 제시해야 하며, 서버는 자신의 현재 rev와 일치할 때만 수용하고 rev를 증가시킨 뒤 브로드캐스트한다. 불일치 시에는 수용하지 않고 발신자에게 거부와 최신 상태를 회신해야 한다. 수용된 변경만이 문서의 정본 이력이 된다.

근거 원인 A-1·A-4·B-1·B-3의 근본 해소

수용 기준 - AC-13-1: 오래된 rev를 제시한 변경이 수용되지 않고 거부 응답이 발신자에게 도달한다. - AC-13-2: 거부를 받은 클라이언트가 최신 상태로 재정박하고, 재정박 후 기준선 불변식(FR-01)이 성립한다. - AC-13-3: 동시 전송된 두 변경 중 정확히 하나만 수용되며, 나머지는 거부된다(양쪽 모두 수용되는 경우 없음). - AC-13-4: 3인 동시 편집 30초 후 서버 rev와 3인의 문서가 모두 일치한다. - AC-13-5: 거부 → 재정박 → 재전송 사이클에서 사용자의 확정 입력이 유실되지 않는다(FR-06과 결합).

우선순위 P1 (FR-12 완료 후)

FR-14 — 발산 감지와 자가 복구

설명 클라이언트 문서와 서버 정본이 어긋난 상태를 감지할 수 있어야 하며, 감지 시 사용자 개입 없이 정본으로 복원되어야 한다. 복원은 미저장 로컬 변경을 조용히 파기하지 않아야 한다.

근거 원인 A-1·A-2·B-3·B-4의 안전망 (G-4)

수용 기준 - AC-14-1: 인위적으로 클라이언트 문서를 오염시키면 일정 시간(예: 다음 변경 교환 시점) 내에 불일치가 감지된다. - AC-14-2: 감지 후 복원이 완료되면 문서가 정본과 일치하고 기준선 불변식이 성립한다. - AC-14-3: 복원 시 캐럿 위치가 합리적으로 보존되거나, 보존 불가함이 사용자에게 표시된다. - AC-14-4: 복원이 무한 반복(복원 → 재발산 → 복원)에 빠지지 않는다.

우선순위 P1

FR-15 — 폭주 변경 차단

설명 문서 전체를 삭제하고 전부 재삽입하는 형태의 변경(기존 코드 주석이 "폭주 diff"라 부르는 것)은 정상 편집으로 간주하지 않고 전송 전에 차단되어야 하며, 대신 재동기화 절차가 수행되어야 한다. 단, 사용자가 실제로 전체 선택 후 삭제·붙여넣기한 정당한 경우는 차단되어서는 안 된다.

근거 원인 기존 방어(dataReady 재동기화)의 보강. A-1·A-2 증상 확대 억제

수용 기준 - AC-15-1: 기준선이 stale인 상태를 인위적으로 만든 뒤 입력하면 폭주 변경이 전송되지 않고 재동기화가 수행된다. - AC-15-2: 사용자가 실제로 전체 선택 후 새 내용을 붙여넣은 경우는 정상 전파된다. - AC-15-3: 차단 발생 시 관측 이벤트가 기록된다.

우선순위 P2

FR-16 — 콘텐츠 채널과 커서 채널의 분리

설명 문서 콘텐츠 변경과 커서·선택 영역 정보는 서로 다른 의미의 데이터이므로, 하나의 불투명 문자열 필드에 실려 같은 처리 경로·같은 영속화 대상을 공유해서는 안 된다. 콘텐츠 변경은 서버 검증(FR-13) 대상이고 커서는 그렇지 않다는 차이가 프로토콜에 드러나야 한다.

근거 원인 §2.3 추가 관측(콘텐츠 diff가 사용자 selection 상태로 Redis 영속화됨) + FR-13 구현 전제

수용 기준 - AC-16-1: 콘텐츠 변경이 사용자 커서 상태 저장소에 기록되지 않는다. - AC-16-2: 커서 메시지 유실이 문서 정합성에 영향을 주지 않는다(커서는 best-effort로 명시). - AC-16-3: 알 수 없는 메시지 타입 수신 시 문서가 변경되지 않는다(현행에는 원문 문자열이 본문을 덮는 경로가 존재 — Caveat 6 참조).

우선순위 P1

6. 메시지 프로토콜 설계

6.1 현행(AS-IS)

발행 /app/selection — 콘텐츠·커서 공용

{
  "sessionId": "<uuid>",
  "documentId": "<wikiId>",
  "userInfo": {
    "id": "<userId>", "name": "...", "color": "#rrggbb",
    "selection": {
      // 불투명 문자열. 서버는 파싱하지 않고 사용자 selection 상태로 Redis 저장 후 그대로 중계
      "message": "{\"type\":\"diff\",\"ops\":[{\"op\":\"retain\"},{\"op\":\"insert\",\"html\":\"<p>..</p>\"}]}"
    }
  }
}

구독 /topic/sessions/{sid}/selections/document/{did} — 위 메시지 원문 그대로(발신자 포함) 구독 /topic/sessions/{sid}/state/document/{did} — {sessionId, documentId, document, revision, participants[]}

결함 - 콘텐츠와 커서가 같은 필드·같은 destination·같은 영속화 대상 (FR-16) - ops에 base·순번·문서 체크섬 없음 (FR-08·FR-13) - op가 위치 인덱스에만 의존 (FR-04) - 거부·확인 응답 채널 없음 (FR-06·FR-13) - document가 null로 채워짐 (FR-12)

6.3 호환 전략

  • protocolVersion 부재 = 구프로토콜로 간주.
  • 신·구 혼재 시 신클라이언트는 구 메시지를 적용하지 않고 재동기화(FR-14)로 처리한다 → 혼재 구간에서 손상 대신 성능 저하를 택한다.
  • 단계 1~2(§7)는 프로토콜을 바꾸지 않으므로 혼재 문제가 없다.

10. 선행 조사 항목

분석서가 미검증 가설로 표기한 항목. 요구사항의 전제로 삼지 않으며, 조사 결과가 나오기 전에는 해당 FR을 확정 착수하지 않는다. 조사는 단계 0에서 수행한다.

ID 조사 대상 근거(분석서) 조사 방법 결과에 따른 처리

§10-5는 특별 취급. 다중 인스턴스라면 FR-13(서버 권위)조차 인스턴스별로 갈라진 정본을 만들어 상황을 악화시킬 수 있다. 단계 3 착수 전 반드시 확정한다.

11. Issues / Caveats

  1. 이 SRS의 사실 근거는 정적 분석이다. 원인 분석서와 이 문서 모두 브라우저 실행 재현을 거치지 않았다. §10의 5개 항목은 조사 전까지 전제로 삼을 수 없다.

  2. 서버 에코 정책은 확정 사실. 서버는 발신자를 제외하지 않고 브로드캐스트하며, 클라이언트가 필터한다. 따라서 A-3은 반증되었고 FR-03은 증상 해소가 아니라 코드 명확화·회귀 방지 목적이다. 우선순위를 P2로 둔 이유다.

  3. FR-05의 (a)/(b) 선택이 미결이다. (a) 블록 내부 병합은 사용자 경험이 우수하나 비용이 크고(단계 6), (b) 우선순위 규칙 + 고지는 단계 3에서 곧바로 얻어진다. 단계 3 완료 시점의 실사용 불만 수준을 근거로 결정할 것을 권한다. 이 SRS는 어느 쪽도 강제하지 않는다.

  4. FR-04 AC-04-4가 미결이다. 블록 안정 식별자를 저장 본문에 남길지(문서 재열람 시 식별자 연속성 확보, 대신 본문 오염) 저장 시 제거할지(본문 청결, 대신 재진입 시 식별자 재발급)는 트레이드오프다. 위키 본문의 외부 참조·검색·버전 비교 기능에 영향을 주므로 해당 기능 담당자와 합의가 필요하다.

  5. OtService 재활용 여부를 이 SRS는 결정하지 않았다. 서버에 revision·history·transform 자산이 이미 존재하며(OtService/OtController), 분석서는 이쪽으로의 이관(R5)이 총비용상 유리할 수 있다고 보았다. 이 SRS는 FR-13을 "서버 권위 수용·거부"라는 성질로만 기술했으므로, 신규 구현과 기존 OT 이관 어느 쪽으로도 충족 가능하다. 단계 3 설계 시 비교 판단할 것.

  6. 범위 외 잠재 버그 (참고). 수신 라우팅에서 type이 diff/cursor가 아닌 메시지는 return 없이 흘러 JSON 문자열 원문이 setData로 들어간다. 현재 타입이 2개뿐이라 미발현이지만, FR-16으로 메시지 타입을 추가하는 순간 문서가 JSON 텍스트로 덮인다. AC-16-3이 이를 커버하나, 단계 3 착수 시 가장 먼저 처리해야 할 항목임을 명시한다.

  7. NFR-01 기준값이 아직 없다. "현행 대비 1.5배 이내"라는 수용 기준은 단계 0에서 기준값을 측정해야 검증 가능해진다. 측정 없이 단계 1을 배포하면 이 NFR은 사후 검증 불가가 된다.

  8. §2.3은 분석서에 없는 추가 관측이다. EditorController.java:179에서 콘텐츠 diff가 사용자 selection 상태로 Redis에 영속화되는 것은 코드에서 직접 확인한 사실이며(분석서 미기재), FR-16의 근거로만 사용했다. 두 증상의 직접 원인은 아니다.

  9. 우선순위는 잠정이다. §10 조사 결과에 따라 FR-08·FR-09·FR-10의 우선순위가 승급/하향될 수 있으며, §10-5 결과에 따라 단계 3 이후 계획 전체가 재검토 대상이다.
