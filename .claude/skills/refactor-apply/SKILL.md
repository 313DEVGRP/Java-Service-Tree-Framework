# 리팩토링 적용

`refactor-action-items` 가 "어디를, 왜, 어떤 방향으로" 고칠지 정리했다면, 이 스킬은 그 아이템 하나를 **동작을 바꾸지 않고** 실제 코드에 옮깁니다. 판단 기준(카테고리 RF/JS, 팀이 정한 결론)은 그 스킬의 가이드북을 그대로 씁니다.

- 자바: `.claude/skills/refactor-action-items/references/guidebook-java.md`
- 자바스크립트: `.claude/skills/refactor-action-items/references/guidebook-js.md`

가이드북 「시작하기 전에 지켜야 할 네 가지」가 이 스킬의 뼈대입니다. **테스트 먼저 → 기능 변경과 섞지 않기 → 작게 바꾸고 매번 테스트.**

## 원칙

- **리팩토링 커밋에는 동작 변경이 하나도 없어야 합니다.** 아이템의 「주의」·「동작 변경 분리」나 「리팩토링이 아닌 발견(F-xx)」에 해당하는 버그는 고치지 않고, 특성화 테스트로 **지금 동작 그대로** 고정해 둡니다. 테스트 이름에 `[현재 동작 고정·F-xx]` 를 붙여 나중에 버그 수정 커밋에서 기대값을 바꿀 테스트임을 알립니다.
- **아이템 범위만 고칩니다.** 같은 파일에 다른 아이템(예: 미사용 코드 삭제 A-32, 이름 A-29)이 걸려 있어도 손대지 않고 보고에만 적습니다. 아이템의 「주의」에 "범위 밖"으로 적힌 위치(다른 단위 EF-2 등)도 마찬가지입니다.
- **커밋하지 않습니다.** 사용자가 요청할 때만 합니다.
- **사용자의 미커밋 변경을 건드리지 않습니다.** 시작할 때 `git status` 를 기록하고, 아이템 위치 파일에 이미 남의 변경(M)이 있으면 그 위에서 작업해도 되는지 먼저 묻습니다.
- **기준 브랜치는 `dev` 입니다.** 모듈이 `dev` 가 아니면 체크아웃을 바꾸지 말고 사용자에게 알린 뒤 지시를 받습니다(점검용 worktree 와 달리, 적용은 사용자 작업 트리에 하므로).
- **설명은 한국어로**, 모듈 규약(Engine-Fire `CLAUDE.md`·`rules/business-pattern.md`, `engine-expert`·`arms-backend-core`·`arms-frontend-web` 스킬)을 따릅니다. Engine-Fire 는 Java 21 이지만 `record` 를 쓰지 않습니다.

## 진행 순서

### 0. 작업 폴더와 기준선

이 저장소 루트의 `CLAUDE.md` 규칙이 있으면 그대로 따릅니다: `tasks/<작업명>/`(task.md · context.md · log.md · sources/ · artifacts/)를 만들고, `task.md` Constraints 에 `target_repo` 와 `write_scope`(1단계는 테스트 경로만, 2단계에서 아이템 위치 파일로 넓힘)를 적고, 외부 repo 를 쓰기 전후로 `_shared/adapters/scope_check.sh` 스냅샷을 비교합니다. 사용자 질문 없이 정한 것은 `log.md` 에 `[DECISION]` 으로 남깁니다.

기준선을 잡습니다.

1. 아이템 원문(대상·#·위치·무엇이 문제인가·이렇게 바꾼다·먼저 할 것·주의·바꾼 모습)을 `sources/` 에 옮겨 둡니다. 엑셀이면 openpyxl 로 「액션 아이템」 시트에서 `대상`·`#` 이 맞는 행을 읽습니다.
2. 아이템의 **줄 번호는 점검 당시 값**입니다. 위치마다 지금 파일을 열어 메소드 이름으로 다시 찾습니다.
3. `git status --short` 와 `git rev-parse --short HEAD` 를 기록합니다.
4. **전체 테스트를 한 번 돌려 실패 목록을 기록합니다.** 나중에 실패가 "원래 있던 것"인지 "내가 만든 것"인지 가르는 기준입니다.
5. 아이템 위치가 속한 도메인의 패키지 순환을 `scripts/package_cycles.py` 로 기록합니다(2·3단계 비교 기준).

### 1. 안전망 — 특성화 테스트 (RF-00)

아이템 「먼저 할 것」에 적힌 대표 입력으로, **위치마다** 지금 코드가 내는 결과를 고정하는 단위 테스트를 씁니다.

- 스프링 컨텍스트 없이 도는 JUnit 5 + AssertJ + Mockito 단위 테스트로 씁니다. 외부 ALM·OpenSearch 의존은 mock 으로 끊습니다.
- 테스트 위치는 대상 클래스와 같은 패키지(`src/test/java/...`), 이름은 `<클래스><아이템 주제>Test`(예: `AlmIssueEntityRecentIdTest`).
- 정상 경로뿐 아니라 경계(null 구성 요소, 구분자가 값 안에 들어간 경우, 형식이 깨진 입력의 예외)까지 **지금 동작 그대로** 고정합니다. 이상해 보여도 고치지 않습니다.
- private 메소드는 그것을 부르는 public 경로로 덮습니다.
- mock 의 기본 반환값(예: `Integer` 반환 메소드는 0)이 실제 객체와 다를 수 있습니다. 값 객체·빈(bean)처럼 만들기 쉬운 타입은 mock 대신 실제 객체를 씁니다.

**커버리지 80%** 는 클래스 전체가 아니라 **아이템 「위치」에 적힌 메소드(와 그 람다)의 라인 커버리지**로 잽니다. 빌드 파일은 고치지 않고 init script 로 JaCoCo 를 붙입니다.

```bash
# Gradle 모듈 (Engine-Fire 등). gradlew 실행 권한이 없으면 sh ./gradlew
sh ./gradlew test --init-script <스킬 경로>/assets/jacoco-init.gradle --tests '*<주제>*'
python3 <스킬 경로>/scripts/method_coverage.py build/reports/jacoco/test/jacocoTestReport.xml \
  'com/arms/api/.../AlmIssueEntity:generateId,recentIdByNewKey' \
  'com/arms/api/.../IssueService:deleteIfDoesNotExistDoc,lambda$deleteIfDoesNotExistDoc$' \
  --min 80 -o <작업 폴더>/artifacts/coverage-before.md
```

80% 에 못 미치면 덮이지 않은 줄을 보고 테스트를 더합니다. 도달할 수 없는 줄(예: 결과가 항상 1개 이상인 `split` 의 `orElseGet` 폴백)은 이유를 적고 넘어갑니다. Maven 모듈은 `jacoco-maven-plugin` 을 명령줄(`org.jacoco:jacoco-maven-plugin:prepare-agent test org.jacoco:jacoco-maven-plugin:report`)로 붙입니다.

화면 스크립트(JS)는 단위 테스트 대신 **화면 확인 목록**(바꾸기 전 동작을 단계별로 적은 표)을 만들고, 가능하면 headless Chrome 으로 바꾸기 전 DOM 결과를 저장해 둡니다.

### 2. 리팩토링

아이템 「이렇게 바꾼다」·「바꾼 모습」대로 바꾸되, **작게 바꾸고 매번 1단계 테스트를 돌립니다.**

- 「바꾼 모습」은 방향을 보여 주는 스케치입니다. 호출하는 곳이 없는 메소드(예: 스케치에만 있는 `withKey`)는 만들지 않습니다.
- 스케치의 이름이 기존 클래스·어노테이션과 겹치면(예: esframework `@RecentId` 와 `RecentId`) 다른 이름을 고르고 `[DECISION]` 으로 남깁니다.
- 내 변경으로 쓰이지 않게 된 import·변수는 지웁니다. 원래 있던 죽은 코드는 지우지 않습니다.
- **1단계 테스트는 고치지 않습니다.** 리팩토링 뒤에도 그대로 통과해야 동작이 같다는 증거가 됩니다. 새로 만든 클래스(값 타입 등)의 테스트는 따로 더합니다.

#### 패키지 구조 (팀 결정)

도메인 표준 구조(`api/<domain>/` 아래 `controller/` · `service/` · `model/dto/`(요청 전용) · `model/vo/`(응답 전용) · `model/entity/` · `model/enums/` · `strategy/`)를 따르고, 리팩토링에서 새로 생기는 클래스는 아래처럼 둡니다.

| 새로 생기는 것 | 위치 · 이름 |
|---|---|
| **값 타입**(값 객체 — 의미와 규칙이 따라다니는 값: recent_id, 금액, 기간 등) | `api/<domain>/model/` **바로 아래**, 하위 패키지 없이. 이름은 개념 그대로(`IssueRecentId`), `VO`·`ValueVO`·`*Value` 접미어 금지. 팀에서 VO 는 응답 객체라 `model/vo/` 에 두면 응답 객체로 읽힌다 |
| 상태·코드 값 | `model/enums/` |
| 요청·응답 객체 | `model/dto/` · `model/vo/` (기존 규칙) |
| 상태 없는 도구 함수 | 그 도메인 안에 두고, 여러 도메인이 쓰는 기술 도구만 `api/util/` |

- **의존 방향**: 값 타입은 `entity`·`dto`·`vo` 를 import 하지 않습니다(자바 표준 라이브러리만). 모든 화살표가 값 타입으로 모여야 순환이 없습니다. 엔티티 → 값 타입 변환이 필요하면 엔티티 쪽 메소드로 둡니다(`entity.recentId()`). `model/vo/` 에 값 타입을 두면 `entity → vo`, `vo → entity` 순환이 생깁니다.
- **주인 도메인**: 여러 도메인이 쓰는 값이라도 주인(그 값이 키·규칙으로 속한 도메인)이 있으면 주인 도메인 `model/` 에 두고 다른 도메인이 import 합니다. 어느 도메인에도 속하지 않는 범용 값만 공용 패키지를 새로 만들며, 그때는 위치를 사용자와 정합니다. `api/util/`(도구 함수)·`egovframework/.../esframework/`(프레임워크)에는 넣지 않습니다.
- **많아지면**: 한 도메인 `model/` 바로 아래 값 타입이 서너 개를 넘어 붐비면 `model/value/` 분리를 사용자에게 제안합니다(자동으로 옮기지 않음).
- 쿼리 필드명(`"recent_id"` 등)은 상수로 빼지 않고 리터럴로 둡니다(Engine-Fire 규약).

#### 리팩토링 중 이런 구조를 만나면 — 순환부터 확인하고 model/ 로 옮긴다

아이템이 손대는 클래스(위치에 적힌 클래스와 그 클래스가 직접 쓰는 값 클래스)에서, **값 타입인데 `model/vo/`·`model/dto/` 등에 들어가 있는 클래스**나 **패키지 순환**을 만나면 다음 순서로 처리합니다.

1. **순환인지 먼저 확인합니다.** 눈으로 판단하지 말고 스크립트로 봅니다.

   ```bash
   python3 <스킬 경로>/scripts/package_cycles.py src/main/java com.arms.api.<domain> \
     --class com.arms.api.<domain>.model.vo.<클래스>
   ```

   출력의 「순환」 묶음과, 그 클래스가 import 하는 도메인 패키지·그 클래스를 import 하는 패키지를 `log.md` 에 남깁니다.
2. **판정합니다.**
   - 그 클래스가 값 타입(의미·규칙이 있는 값, 응답으로 내보내는 객체가 아님)이고 같은 도메인의 `entity`·`dto`·`vo` 를 import 하지 않으면(스크립트 판정 "model/ 로 옮겨도 순환이 생기지 않는다") → **`model/` 바로 아래로 옮깁니다.**
   - 값 타입인데 도메인 패키지를 import 하고 있으면 → 그 의존(예: 엔티티를 받아 값을 만드는 메소드)을 상대 쪽(엔티티의 메소드)으로 먼저 옮긴 뒤 다시 스크립트를 돌리고 옮깁니다.
   - 응답 VO·요청 DTO 끼리의 순환(값 타입이 아님)은 옮기지 않습니다. 이 스킬 범위가 아니므로 4단계 점검의 「그 밖의 후보」(RF-11 구조)로 남깁니다.
3. **옮기는 것은 별도 단계로 합니다.** 패키지 선언과 import 만 바꾸는 이동을 한 단계로 하고, 1단계 테스트를 돌려 통과를 확인한 뒤 다음 변경으로 넘어갑니다. 테스트 파일도 같은 패키지로 옮깁니다. 다른 모듈·다른 도메인이 그 클래스를 import 하고 있으면 그 import 도 함께 바꾸고, 바꾼 파일을 보고에 적습니다.
4. **옮긴 뒤 스크립트를 다시 돌려** 그 클래스가 순환 묶음에서 빠졌는지(또는 새 순환이 생기지 않았는지) 확인하고 결과를 `log.md` `[VERIFICATION]` 에 남깁니다.

아이템이 손대지 않는 곳에서 본 순환·잘못 놓인 값 타입은 옮기지 않고 위치만 「그 밖의 후보」에 적습니다.

### 3. 검증

1. 1단계 테스트 + 새 테스트가 모두 통과하는지, 1단계 테스트 파일에 변경이 없는지 확인합니다.
2. `method_coverage.py` 로 리팩토링 뒤 커버리지를 다시 재고(새 값 타입은 `'<클래스>:*'`), `coverage-after.md` 로 저장합니다.
3. 아이템 「무엇이 문제인가」의 패턴이 남았는지 grep 으로 확인합니다(예: `"_" +` 조립, `split("_")`). 남은 것은 다른 아이템 범위(미사용 코드 등)인지 하나씩 이유를 붙입니다.
4. 전체 테스트를 돌려 0단계 실패 목록과 비교합니다. 새 실패가 있으면 고치거나 되돌립니다.
5. **적용한 변경을 diff 로 저장합니다**(`git diff > artifacts/<아이템>-refactor.diff`, 새 파일은 `git diff --no-index /dev/null <파일>` 로 덧붙임). 작업 트리가 밖에서 되돌려져도 다시 적용할 수 있어야 합니다.
6. 새 클래스를 만들었거나 클래스를 옮겼으면 `package_cycles.py` 로 도메인 패키지를 다시 검사해, 0단계보다 순환이 늘지 않았는지 확인합니다.
7. `scope_check.sh` 로 write_scope 밖 변경이 없는지 확인합니다. 내가 건드리지 않은 파일이 바뀌었으면 되돌리지 말고 보고합니다.

### 4. 리팩토링 결과 점검

`refactor-action-items` 스킬 절차(2~7단계)를 **이번 변경 파일만** 대상으로 돌려, 리팩토링 뒤에 새로 보이는 문제를 액션 아이템으로 남깁니다(`refactoring-action-items/<날짜>-<모듈>-<아이템>-리팩토링결과.md` + PDF + xlsx). 원래 엑셀에 이미 있는 아이템·발견(같은 문제)은 다시 올리지 않고, 위치만 옮겨진 발견은 "기존 F-xx 위치 이동"으로 적습니다.

### 5. 보고
