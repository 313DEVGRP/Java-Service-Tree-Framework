# 리팩토링 액션 아이템

이 스킬은 코드를 **고치지 않습니다.** 팀 리팩토링 가이드북을 기준으로 "어디를, 왜, 어떤 방향으로 고쳐야 하는지"를 액션 아이템으로 정리해, 개발자가 읽고 직접 작업하거나 이슈로 옮길 수 있게 하는 것이 목적입니다.

좋은 액션 아이템은 읽는 사람이 **그 코드를 처음 보더라도** 무엇이 문제인지, 고치면 무엇이 좋아지는지, 어디서부터 손대면 되는지 알 수 있어야 합니다. 그래서 위치는 정확해야 하고, 설명은 단어를 나열하지 말고 문장으로 씁니다. 팀원들이 가장 불편해했던 것이 "근거 출처만 잔뜩 있고 정작 무슨 말인지 모르겠는" 문서였다는 점을 기억하세요.

## 진행 순서

### 1. 대상 정하기

- 사용자가 파일·폴더를 지정했으면 그 범위를 점검합니다.
- 지정이 없으면 **현재 git 변경분**을 점검합니다. 이 저장소 루트 아래 `Java-Service-Tree-Framework-*` 모듈은 각각 별도 git 저장소이므로, 모듈마다 `git -C <모듈> status --porcelain`으로 변경이 있는 모듈을 찾고 그 모듈들만 봅니다.
- 범위가 너무 넓으면(예: 모듈 전체) 그대로 진행하되, 후보가 많은 파일부터 상위 몇 개 파일에 집중하고 나머지는 "그 밖의 후보"로 요약한다고 사용자에게 한 줄로 알립니다.

### 2. 후보 탐지

```bash
python3 .claude/skills/refactor-action-items/scripts/scan.py <파일|폴더> [...]
python3 .claude/skills/refactor-action-items/scripts/scan.py --diff <모듈 경로> [...]   # 변경분만
```

스크립트는 카테고리별 신호(긴 함수, 같은 switch 반복, 문자열 상태 비교, `return null`, `console.log`, 이스케이프 없는 HTML 문자열, `async: false`, 복사본에 가까운 함수 쌍 등)를 줄 번호와 함께 보여 줍니다.

탐지 결과는 **후보일 뿐**입니다. 스크립트는 글자 모양만 보기 때문에 놓치는 것도 있고 잘못 잡는 것도 있습니다. 특히 "남의 데이터만 만지는 메소드", "이름과 다른 동작", "응답 VO가 도메인 객체로 쓰임" 같은 문제는 코드를 읽어야만 보이므로, 후보 주변을 읽으면서 이런 것도 함께 찾습니다.

### 3. 기준 읽기

언어에 맞는 가이드북을 읽습니다. 액션 아이템마다 해당 카테고리 절의 "가이드 방향"을 기준으로 판단하고, "이렇게 바꾼다"의 예시를 참고해 방향을 씁니다.

- 자바: `references/guidebook-java.md` — RF-00~RF-12, 객체지향 생활 체조, VO와 도메인 객체
- 자바스크립트: `references/guidebook-js.md` — JS-00~JS-13

가이드북 전체를 매번 다 읽을 필요는 없습니다. 아래 「판단 기준 요약」으로 먼저 분류하고, 해당 카테고리 절만 찾아 읽으면 됩니다.

### 4. 원문 확인과 판단

후보마다 실제 코드를 읽고 다음을 정합니다.

- **정말 문제인가.** 가이드북 기준에 비춰 고칠 가치가 있는지 판단합니다. 걸리긴 하지만 고칠 필요가 없으면 버립니다. 예를 들어 정상 경로가 둘인 if/else, 데이터를 실어 나르는 DTO의 getter/setter는 문제가 아닙니다.
- **묶을 수 있는가.** 같은 원인에서 나온 후보는 하나의 액션 아이템으로 묶습니다. `console.log` 70곳은 아이템 70개가 아니라 "이 파일의 디버깅 로그 정리" 하나입니다. 같은 switch가 4곳에 있으면 아이템 하나에 위치 4곳을 적습니다.
- **리팩토링인가.** 동작을 바꿔야 고쳐지는 문제(버그 의심)나 보안 문제는 리팩토링 아이템에 섞지 않고 「리팩토링이 아닌 발견」에 따로 적습니다. 리팩토링은 동작을 바꾸지 않는 작업이라, 섞으면 리팩토링 커밋에 동작 변경이 들어가게 됩니다.

줄 번호는 반드시 실제 파일에서 확인한 값을 씁니다. 스크립트 출력이나 기억에 기대어 추정한 번호를 쓰지 않습니다.

### 5. 우선순위와 개수

| 우선순위 | 기준 |
|---|---|
| 높음 | 고치지 않으면 다음 수정 때 버그가 생기기 쉬운 것 — 같은 분기·같은 코드가 여러 곳(하나만 고치고 빠뜨리기 쉬움), 실패를 숨겨 잘못된 데이터가 만들어질 수 있는 오류 처리, 여러 요청이 함께 쓰는 가변 상태, 늦은 응답이 화면을 덮어쓰는 비동기 순서 |
| 중간 | 읽고 고치는 데 시간이 많이 드는 것 — 긴 함수, 큰 클래스·파일, 많은 인수, 문자열 상태 코드, 하드코딩된 주소·설정 |
| 낮음 | 정리 수준 — 주석 처리된 코드, 디버깅 로그, 이름 |

액션 아이템은 **최대 15개**까지 자세히 씁니다. 사람이 한 번에 읽고 처리할 수 있는 양을 넘으면 목록 자체가 무시되기 때문입니다. 나머지는 「그 밖의 후보」에 한 줄씩만 적습니다. 우선순위가 높은 것부터 씁니다.

### 6. 작성

아래 「액션 아이템 형식」을 따릅니다.

- 설명은 문장으로 씁니다. "중복·결합도·가독성 저하"처럼 단어만 나열하지 않습니다.
- 책 이름, 장 번호, 휴리스틱 코드 같은 근거 출처는 쓰지 않습니다. 카테고리 코드(RF-06, JS-10)만 붙입니다.
- 코드 스케치는 짧게, **그 모듈의 스택에 맞게** 씁니다. Engine-Fire는 Java 21이지만 `record`를 쓰지 않습니다. Backend-Core는 Java 11 / Boot 2.6입니다. Frontend-Web `arms/`는 jQuery이고 주변 코드의 ES5/ES6 스타일을 따릅니다. 모듈 규약이 헷갈리면 해당 도메인 스킬(`engine-expert`, `arms-backend-core`, `arms-frontend-web`)의 규약을 확인합니다.
- "먼저 할 것"에는 안전망을 적습니다. 자바는 그 코드의 현재 동작을 고정하는 테스트, 화면 코드는 바꾸기 전 화면 확인 목록입니다.
- 바꾸면 동작이 달라질 수 있는 지점이 보이면 "주의"에 적습니다. 예를 들어 분기를 표로 바꿀 때 원래 코드의 한 분기만 다르게 동작하는 경우입니다.

### 7. 저장과 보고

- 결과를 `refactoring-action-items/<YYYY-MM-DD>-<대상 이름>.md`(작업 루트 기준)에 저장합니다. 폴더가 없으면 만듭니다. 같은 이름이 있으면 뒤에 `-2`처럼 번호를 붙여 덮어쓰지 않습니다.
- 화면 답변에는 요약 표(아이템 번호·카테고리·위치·한 줄 요약·우선순위), 우선순위 높음 아이템의 핵심 한두 문장, 「리팩토링이 아닌 발견」이 있으면 그 내용, 저장한 md·PDF 파일 경로를 적습니다. 파일 내용 전체를 화면에 다시 붙이지 않습니다.
- md를 저장한 뒤에는 **항상 PDF로도 변환합니다.** 같은 폴더에 같은 이름의 `.pdf`가 생깁니다. 회의 자료로 돌리거나 인쇄해서 보는 경우가 많아서, A4에 맞추고 표와 코드 블록이 쪽 사이에서 잘리지 않게 해 두었습니다. md를 고친 뒤에는 PDF도 다시 만들어 두 파일의 내용을 맞춥니다. 변환이 실패하면(Chrome이나 `markdown`·`pygments` 패키지가 없는 경우 등) md는 그대로 두고, 실패 이유를 답변에 적습니다.

  ```bash
  python3 .claude/skills/refactor-action-items/scripts/to_pdf.py refactoring-action-items/<파일>.md
  ```

### 팀이 정한 판단 기준 (책끼리 다른 지점의 결론)

- 두 경우가 모두 정상적인 흐름이면 if/else 는 문제가 아닙니다. 예외적인 경우를 먼저 빠져나가지 않아 깊어진 경우만 대상입니다.
- 모든 int·String 을 감쌀 필요는 없습니다. 의미와 규칙이 따라다니거나 순서를 바꿔 넣기 쉬운 값만 대상입니다.
- 줄 수·필드 수 같은 숫자는 신호일 뿐입니다. "이름 하나로 설명할 수 있는가", "바뀌는 이유가 하나인가"로 판단합니다.
- getter 체인은 반복되거나 중간 구조가 바뀔 곳만 대상입니다. 스트림·빌더 체인은 아닙니다.
- getter/setter 를 문제 삼는 것은 업무 로직을 가진 도메인 객체뿐입니다. 요청 DTO·응답 VO 는 대상이 아닙니다.
- Engine-Fire 에서 DTO 는 요청, VO 는 응답 전용입니다. VO 를 만드는 변환 로직(`fromEntity()` 등)은 길어도 VO 안에 두는 것이 팀 규칙입니다. 업무 규칙이나 조회가 필요한 판단만 VO 밖(도메인 객체)으로 옮깁니다.
- 응답 VO 와 도메인 객체를 함께 쓰는 것 자체는 문제가 아닙니다. 밖에 보이면 안 되는 값이 생겼을 때, 받는 쪽마다 모양이 다를 때, 외부 공개 API일 때, 업무 규칙이 쌓일 때만 나누라는 아이템을 씁니다.
- 검사/비검사 예외는 "호출자가 미리 막을 수 있는 실패인가"로 정합니다.

````markdown
## 그 밖의 후보

자세히 다루지 않은 후보입니다. 위 아이템을 처리한 뒤 다시 점검할 때 참고합니다.

- `<경로>:<줄>` [카테고리] <한 줄>
````

리팩토링이 아닌 발견이 없으면 그 절에 "없음"이라고 적습니다. 그 밖의 후보가 없으면 그 절은 생략합니다.

아이템과 발견은 하나씩 "항목 | 내용" 표로 씁니다. 표 하나만 보면 그 아이템을 처리할 수 있게 하려는 것입니다. 마크다운 표는 한 행이 한 줄이어야 하므로 다음을 지킵니다.

- 칸 안에서 줄을 바꿀 때는 `<br>`을, 목록은 `• `을 씁니다.
- 내용에 `|`가 들어가면 `\|`로 적습니다. 그러지 않으면 열이 갈라집니다.
- 코드 블록은 표 칸에 넣을 수 없으므로 표 바로 아래에 `*원문*`, `*바꾼 모습*` 제목을 달아 둡니다.
