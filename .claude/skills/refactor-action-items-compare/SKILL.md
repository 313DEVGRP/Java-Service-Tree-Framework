# 리팩토링 액션 아이템 — 10-06 양식 + 이전 판 비교

이 스킬은 코드를 **고치지 않습니다.** 점검 방법은 `refactor-action-items` 스킬과 같고, 결과 엑셀의 양식과 이전 판 비교 시트만 다릅니다. 두 스킬의 판단 기준이 따로 놀지 않도록 점검 절차는 그 스킬의 문서를 그대로 씁니다.

## 진행 순서

### 1~6단계 — refactor-action-items 와 같음

`.claude/skills/refactor-action-items/SKILL.md` 를 먼저 읽고 다음을 그대로 따릅니다.

- 1단계 대상 정하기(dev 기준 worktree, 넓은 범위의 패키지별 병렬 점검 포함) ~ 6단계 작성
- 「판단 기준 요약」, 「팀이 정한 판단 기준」, 「액션 아이템 형식」
- 스크립트: 후보 탐지 `.claude/skills/refactor-action-items/scripts/scan.py`, PDF `.claude/skills/refactor-action-items/scripts/to_pdf.py`
- 병렬 점검을 하면 각 에이전트에게 넘기는 SKILL.md 경로도 위 파일입니다. md 를 쓰는 규칙은 같습니다.

md 의 `난이도`·`권장 단계`·`선행 아이템`·`동작 변경 분리` 행은 이 스킬의 엑셀에 열이 없어 들어가지 않습니다. md 에는 그대로 써 둡니다(나중에 10-05 양식으로 다시 뽑을 수 있게).

### 7. 저장과 보고 — 이 스킬

- md 와 PDF 는 refactor-action-items 7단계와 같습니다: `refactoring-action-items/<YYYY-MM-DD>-<대상 이름>.md`, 같은 이름의 `.pdf`. 같은 이름이 있으면 `-2` 처럼 번호를 붙여 덮어쓰지 않습니다.
- 엑셀은 **이 스킬의** 변환기로 만듭니다. 양식은 `2026-10-06-전체.xlsx` 와 같습니다.

  ```bash
  # 대상 하나
  python3 .claude/skills/refactor-action-items-compare/scripts/to_xlsx.py refactoring-action-items/<파일>.md
  # 여러 대상을 합치고 이전 판과 비교
  python3 .claude/skills/refactor-action-items-compare/scripts/to_xlsx.py refactoring-action-items/<날짜>-*.md \
      -o refactoring-action-items/<날짜>-전체.xlsx --compare A-RMS_리팩토링_액션아이템_2026-10-05.xlsx
  ```

  - 「액션 아이템」: 대상 · # · 카테고리 · 우선순위 · 제목 · 위치 · 무엇이 문제인가 · 왜 수정이 필요한가 · 이렇게 바꾼다 · 먼저 할 것 · 주의 · 원문 · 바꾼 모습 · 담당자 · 상태(드롭다운: 미착수/진행 중/완료/보류/하지 않음) · 비고
  - 「리팩토링이 아닌 발견」, 「그 밖의 후보」, 「점검 대상」(대상별 점검 범위·점검일·건수)
  - 「<MM-DD> 비교」(`--compare` 를 줄 때): 기준판의 액션 아이템·발견 하나가 한 행입니다. 열은 모듈 · 구분 · 기준 ID · 기준 우선순위 · 기준 제목 · 기준 위치 · 새 대상·# · 새 제목 · 판정 · 비고이고, 기준판에 대응이 없는 새 항목은 '신규' 행으로 붙습니다. 오른쪽에 판정별 건수 수식이 있습니다.

- **비교 기준판**: 사용자가 따로 말하지 않으면 작업 루트의 `A-RMS_리팩토링_액션아이템_2026-10-05.xlsx` 입니다. 기준판은 `액션아이템`·`위치상세`·`리팩토링외발견` 시트가 있는 A-RMS 양식이어야 합니다. 이번 결과에 없는 모듈(예: 점검하지 않은 Frontend-Web)은 비교하지 않습니다.

- **비교 판정 규칙**(변환기가 먼저 정하고 메인이 확인합니다)
  - 같은 모듈에서 제목·내용이 가장 비슷한 새 항목(유사도 0.6 이상)이 있으면 그것과 대응시키고 '유지'로 둡니다.
  - 없으면 같은 파일·줄 ±5 위치의 새 항목 중 제목이 어느 정도 비슷한 것과 대응시킵니다. 위치만 겹치고 원인이 다른 항목은 비고에 '원인 다름'으로 따로 적습니다.
  - 대응이 없으면 '확인 필요'입니다. **'확인 필요'는 반드시 원문을 확인해 판정합니다.** 흔한 경우는 이렇습니다.
    - 모듈 전체 아이템(예: 테스트 없음)이 단위별 아이템으로 나뉘었습니다 → '변경'
    - 점검 범위가 java 로 한정되어 resources(yml 등)의 발견이 빠졌습니다 → md 에 되살리고 '유지'
    - 코드가 바뀌어 문제가 사라졌습니다 → '해소'
  - 판정을 정했으면 JSON 으로 적어 `--overrides` 로 다시 만듭니다. 새 항목 키는 `<대상> <#>` 형식입니다(예: `Backend-Core BC-2 A-01`).

    ```json
    {"BC-07": {"verdict": "변경", "new_ids": ["Backend-Core BC-2 A-01", "Backend-Core BC-5 A-09"], "note": "모듈 테스트 아이템을 범위별로 나눔"}}
    ```

  - 판정 값: 유지 · 변경(같은 문제를 범위·방향을 바꿔 다시 씀) · 해소(코드에서 문제가 사라짐) · 확인 필요 · 신규.

- **여러 단위를 합칠 때 확인할 것** (refactor-action-items 의 '합치기'에 더해)
  - 같은 모듈의 다른 단위에 제목이 거의 같은 아이템이 있으면 한 아이템으로 모읍니다. 지운 쪽의 위치를 남길 쪽으로 옮기고, 지운 아이템 ID 를 참조하는 곳(선행 아이템·후보 메모)을 고칩니다. 양쪽 md 의 「리뷰 반영」 절에 기록합니다.
  - 단위끼리 서로 반대되는 전제(예: 같은 메소드가 '없으면 예외' 와 '없으면 null')가 보이면 원문으로 확인하고 틀린 쪽을 고칩니다.

- 화면 답변에는 refactor-action-items 7단계의 내용에 더해, 비교 시트의 판정별 건수와 '확인 필요'를 어떻게 판정했는지를 적습니다.
